1. Project Overview

ShowSzn is a full-stack movie ticket booking platform modeled on BookMyShow: browse movies by city, view showtimes across multiple cinema chains, pick seats on a real seat map, and book with a live (Redis-backed) seat-locking flow. It also has a lightweight Events section and an admin panel for managing the catalog.

DatabaseMySQL 8.4Migrated from PostgreSQL mid-project; schema managed by Flyway

The build order across the project was: scaffolding → data model → auth → browse (movies/shows) → admin panel → geolocation + trailers + UI polish → scalability (pagination, caching, more cities) → MySQL migration + realistic multi-mall venues + corrected movie/trailer catalog → full booking & seat-selection flow → site structure (logo, search, footer, category nav, events, banners).

4. Authentication & Authorization Flow

1 User clicks "Sign in" → Clerk's hosted modal handles sign-up/sign-in (frontend only, via @clerk/clerk-react).
2 Clerk issues a session JWT. useAuthTokenInjector attaches it as Authorization: Bearer <token> on every axios request.
3 Spring Security's OAuth2 resource server validates the JWT against Clerk's JWKS (fetched from {CLERK_ISSUER}/.well-known/openid-configuration), lazily and cached.
4 ClerkJwtAuthenticationConverter runs on every authenticated request: looks up app_user by the JWT's sub claim, and if is_admin = true, grants the ROLE_ADMIN authority.
5 On endpoints that need a persisted user (e.g. /api/me, booking confirm), UserSyncService.syncFromJwt() creates or updates the app_user row from the JWT's sub/email/name claims.
6 Bootstrap admins: the ADMIN_EMAILS env var (comma-separated) is checked on every sync — any matching email is auto-promoted to admin, even on a fresh database. No manual SQL needed.

5. Booking & Seat-Locking Flow

The seat map is public (no auth needed to view). Holding and confirming seats requires authentication. Redis is the source of truth for temporary holds — the database's show_seat.status only ever transitions AVAILABLE → BOOKED, never to an intermediate "locked" state, which avoids needing a background cleanup job for expired holds (Redis TTL handles that automatically).

1 View seat map — GET /api/public/shows/{id}/seat-map. For each seat: DB status BOOKED → shown as booked; else Redis key seatlock:{showSeatId} exists → shown as locked; else available.
2 Select seats — client-side only, no server call yet.
3 Hold — POST /api/bookings/hold {showId, showSeatIds}. For each seat, SETNX seatlock:{id} = holdId with a 5-minute TTL. If any seat is already locked, the whole request fails with 409 and any locks acquired so far in that request are rolled back. On success, hold metadata (user, show, seats, total) is stored as JSON under hold:{holdId}, same TTL.
4 Pay — currently a mock: clicking "Pay & Confirm" calls confirm directly with no real payment gateway (see §11 — Stripe keys were never supplied).
5 Confirm — POST /api/bookings/confirm {holdId}. Validates: hold exists, belongs to the caller, and every seat's lock still points to this holdId (defends against a lock expiring mid-flow). Then, in one DB transaction: creates the Booking row, one BookingSeat row per seat, flips every ShowSeat.status to BOOKED, and finally deletes the Redis lock keys.

Why Redis SETNX and not a DB row lock?

Using Redis avoids two problems a DB-only design would have: (a) a hold that's never confirmed (user closes the tab) would leave seats stuck in a "locked" state forever without a cleanup job, and (b) checking-then-setting seat status in the DB under concurrent requests needs pessimistic locking or careful transaction isolation to avoid a race where two users both see a seat as available. Redis's SETNX ... EX is atomic and self-expiring, which sidesteps both.

6. Caching Strategy

Two hot, read-heavy, rarely-changing public endpoints are cached in Redis via Spring's @Cacheable: the city list (cities cache) and "movies playing in city X" (moviesByCity cache, keyed by city ID). TTL is 5 minutes. Cache is evicted (@CacheEvict(allEntries = true)) whenever an admin creates/updates/deletes a movie, or creates a show — either could change what's "now showing" in a city.

Bug found & fixed: Spring Boot's default Redis cache serializer (GenericJacksonJsonRedisSerializer) loses the element type of generic collections like List<CityResponse> on deserialize — Jackson has no way to know the target type from a cache lookup alone, so it falls back to List<LinkedHashMap>. This threw HttpMessageNotWritableException when serving a cache hit, which — critically — doesn't surface as a 500. Spring's error-handling re-dispatches to /error internally, which isn't covered by the /api/public/** permit-all rule, so it fell through to "authentication required" and returned a misleading 401 instead. Fixed by registering a per-cache-name RedisCacheConfiguration with an explicitly-typed JacksonJsonRedisSerializer (concrete JavaType per cache, no generic type erasure possible). See cache/CacheConfig.java.

This project runs on a very recent Spring Boot 4 / Jackson 3 stack, where Jackson's Maven coordinates moved from com.fasterxml.jackson.* to tools.jackson.*. Spring Data Redis's classic GenericJackson2JsonRedisSerializer (the "2" suffix) is hardcoded to the old Jackson 2 API and isn't on the classpath at all in this stack — the Jackson-3-compatible replacement is GenericJacksonJsonRedisSerializer (no "2"). This is worth knowing if the Jackson/Redis dependency versions ever get bumped again.

State management patterns

  • Server state: entirely TanStack Query. Every domain has its own hooks file (queries.ts for public browse, adminQueries.ts, bookingQueries.ts). Mutations invalidate the relevant query keys on success rather than manually patching cache.
  • Selected city: CityContext, persisted to localStorage under showszn.selectedCityId. On first visit with no stored preference, CitySelector tries navigator.geolocation and picks the nearest seeded city via Haversine distance (lib/geo.ts); falls back to the first city if denied or unsupported.
  • Auth token: useAuthTokenInjector is called once near the app root; it registers an axios request interceptor that calls Clerk's getToken() and attaches it as a Bearer header on every request (harmless no-op on public endpoints).
  • Pagination: admin list pages carry their own page state and read Spring's Page<T> response shape (content, totalPages, etc.) via a shared Pagination component. Dropdowns that need the full list (e.g. picking a venue when creating a show) use separate useAllAdminVenues/useAllAdminMovies hooks that request a large page size rather than reusing the paginated hook.

Recurring bug pattern: lazy-loaded associations masked as 401

Found three separate times in different services (catalog shows, admin venues, admin shows): accessing a lazily-fetched JPA association (e.g. show.getScreen().getVenue().getName()) outside an open Hibernate session throws LazyInitializationException. Because this happens during JSON response serialization — after the controller method has already returned — Spring's error-dispatch mechanism re-enters the servlet pipeline via /error, which isn't covered by the security config's permit-all rule, so it returns 401 Unauthorized instead of a 500. This is deeply misleading: it looks like an auth bug when it's actually a data-access bug.

Fix pattern used throughout: add JOIN FETCH to the repository query so every association the DTO mapper touches is loaded in the same query, eliminating the lazy proxy entirely rather than trying to keep the transaction open longer.

11. Known Limitations & Next Steps

Payment is mocked. No Stripe keys have been supplied, so POST /api/bookings/confirm finalizes the booking immediately with no real charge. Wiring real Stripe would mean: creating a PaymentIntent during hold, confirming it client-side, and only finalizing the booking from a webhook (not the client) so a browser closing mid-payment can't create a booking without a successful charge.
Plays, Sports, and Activities are placeholder pages. Building these out fully would mean replicating the entire catalog + booking domain (venue/screen-equivalent, seat-or-ticket inventory, its own admin CRUD) for each category — a significant scope expansion intentionally deferred.
Events are browsable only. No seat/ticket booking model exists for events yet — the event table has no relationship to booking.
Public movie listing isn't paginated. Only admin list endpoints (movies/venues/shows) are paginated. The public "now showing" list is naturally bounded per city today, but would need pagination if the catalog grows much larger.
No automated tests. All verification in this build was done via manual curl checks, compile/boot checks, and browser testing by the user. There is no test suite (unit, integration, or e2e) yet.

Suggested next steps, roughly in priority order

  1. Wire real Stripe payments (webhook-driven confirmation, not client-driven)
  2. Add a "My Bookings" page on the frontend (the backend endpoint GET /api/bookings already exists and is unused by the UI)
  3. Add automated tests, starting with the seat-lock concurrency logic (highest-risk correctness surface)
  4. Add booking cancellation/refund flow
  5. Consider a background job to expire stale PENDING bookings if the payment step becomes asynchronous
